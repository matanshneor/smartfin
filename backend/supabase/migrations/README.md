# מיגרציות

**המצב תקין: 36 מקומיות, 36 רשומות בשרת.** `supabase db push` עובד.

זה לא היה המצב עד ה-20 בספטמבר 2026. הפנקס בשרת הכיר רק 5 מתוך 34
המיגרציות, ושתי רשומות מוקדמות (`20260527172248`, `20260527172300`) היו
רשומות בשרת בלי קובץ מקומי — הן נוצרו דרך לוח הבקרה לפני שה-CLI נכנס
לשימוש. בגלל זה `db push` היה מסוכן: הוא היה מנסה לשחזר את כל המיגרציות
ממאי ואילך על מסד שכבר יש בו הכול. שתי הרשומות היתומות שוחזרו לקבצים
אמיתיים מתוך עמודת ה-`statements` בטבלת ההיסטוריה, במקום להימחק.

## איך מוסיפים מיגרציה

1. כותבים את הקובץ כאן, בשם `<YYYYMMDDHHMMSS>_<תיאור>.sql`.
2. **הרצה יבשה מול הנתונים האמיתיים** — זה לא אופציונלי:

   ```
   supabase db query "begin; $(cat supabase/migrations/<file>.sql) rollback;" --linked
   ```

   `supabase db query` מכבד `rollback`, כך שאפשר להריץ מיגרציה שלמה על
   נתוני הייצור ולראות מה היא עושה בלי לשנות דבר. לבדיקת RLS או פונקציות
   `SECURITY DEFINER`, מדמים משתמש מאומת בתוך אותה טרנזקציה:

   ```sql
   select set_config('request.jwt.claims', json_build_object('sub','<uuid>')::text, true);
   set local role authenticated;
   ```

3. רק אז `supabase db push --linked` (או `--dry-run` קודם).

## מה לא לעשות

`supabase migration repair --status reverted` **מוחק** שורה מפנקס
ההיסטוריה. ה-CLI מציע את זה כשיש רשומה בשרת בלי קובץ מקומי — אל תעשו
את זה לפני שהוצאתם את ה-SQL שלה מעמודת `statements` ושמרתם אותו כקובץ.
זה הרישום היחיד שקיים לשינוי הזה.
